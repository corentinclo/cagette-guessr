# CagetteGuessr — Refonte complète du repo

## Objectif

Le dépôt ne doit plus ressembler en aucune manière au dépôt initial `Worldguessr`. Il doit être pensé comme un projet nouveau, spécifique à `CagetteGuessr`, avec une identité propre, un code refait à zéro et une architecture adaptée à la vision du produit.

Le but n'est pas de faire une simple adaptation ou un fork visuel, mais de reconstruire l'application comme si elle avait été créée dès le départ pour CagetteGuessr.

## Principe directeur

- Supprimer toute dépendance explicite à la structure, au branding et à l'architecture originelle de `Worldguessr`.
- Renommer et réorganiser les composants, fichiers, modules et variables pour correspondre au projet CagetteGuessr.
- Repenser l'expérience utilisateur, les fonctionnalités et la logique métier pour refléter le contexte du jeu et de l'écosystème Cagette.
- Faire en sorte que le dépôt ait l'impression d'avoir été conçu de zéro pour ce projet, et non comme une copie modifiée d'un autre repo.

## Règles de refonte

### 1. Identité du projet
- Le nom du projet doit être cohérent avec `CagetteGuessr` dans toute la base de code.
- Les titres, textes, messages et labels doivent être adaptés à la marque et au ton du produit.
- Les références à `Worldguessr` doivent être supprimées ou remplacées par des éléments propres à CagetteGuessr.

### 2. Structure du dépôt
- La hiérarchie des dossiers ne doit plus refléter celle du repo d'origine.
- Les fichiers doivent être renommés ou remaniés pour correspondre à la nouvelle architecture.
- Les modules, services, composants et utilitaires doivent être regroupés selon une logique propre au projet cible.

### 3. Code et logique
- Le code ne doit pas être considéré comme un simple fork technique.
- Les fonctionnalités doivent être réécrites avec une logique de projet adaptée à CagetteGuessr.
- Les conventions internes, nommage et organisation doivent être cohérentes avec une application reconstruite de zéro.

### 4. UX / UI
- L'interface ne doit pas conserver les éléments visuels ou les choix de conception hérités de l'ancien repo.
- Le design doit donner l'impression d'un produit original, propre à CagetteGuessr.
- L'expérience utilisateur doit être pensée pour le jeu, la navigation et l'engagement de manière native au projet.

### 5. Documentation et contexte
- La documentation du projet doit parler de CagetteGuessr comme un projet autonome.
- Les README, specs et notes doivent refléter la vraie vision du produit, sans traces de l'ancien dépôt.
- Toute référence historique à `Worldguessr` doit être évitée sauf si elle est explicitement documentée comme référence externe non représentative.

## Exigence finale

Le repository doit être lisible comme un projet entièrement original, créé spécifiquement pour CagetteGuessr, avec une architecture, un nommage, une identité visuelle et un code qui ne laissent aucune ambiguïté sur le fait qu'il ne s'agit pas d'un simple remix du repo `Worldguessr` initial.

En résumé : la base de code doit avoir l'apparence, la logique et la cohérence d'un projet né de zéro pour CagetteGuessr.
